## 1. AI 协同工作流（核心原则）

### 1.1 先说后写，确认后动
* **原则**：AI 在动手写任何核心脚本或功能代码之前，**必须先和用户进行对齐与确认**。
* **优秀 Prompt 示例**：
  > "帮我写一个敌人巡逻脚本。**先列出你打算用的变量名和方法名，我确认后再写代码。**"
* **AI 行为规范**：
  1. 收到功能需求后，先构思类结构。
  2. 列出拟使用的**类名**、**变量名**（包括其数据类型与含义）以及**方法名**（包括入参和返回值类型）。
  3. 在实际写入代码前，AI 必须列出本次改动会影响到哪些其他文件或模块，确认无误。
  4. 等待用户确认。用户提出修改意见后进行调整；用户确认无误（或给予批准）后，AI 才能实际写入/修改文件。

### 1.2 最小改动原则
* **原则**：AI 每次只能修改与当前任务直接相关的代码。如果发现其他地方有问题或"可以优化"，必须先向用户报告，获得许可后才能动手，严禁顺手修改。

### 1.3 需求不明时必须暂停
* **原则**：如果需求描述存在歧义，或涉及未在说明书中定义的内容，AI 必须停下来列出疑问并向用户确认，严禁自行假设后直接实现。

### 1.4 架构不得擅自重组
* **原则**：未经用户明确授权，AI 不得对现有类结构、文件组织、模块划分进行重构或合并，即使 AI 认为新结构"更合理"。

### 1.5 完成播报规范
* **原则**：每次完成一个任务后，AI 必须用固定格式汇报：
  * ✅ 修改了哪些文件（列出文件名）
  * ✅ 新增/删除了哪些变量（需与 `变量.md` 同步状态一致）
  * ⚠️ 遗留问题或需要用户注意的风险点

### 1.6 代码必须完整输出
* **原则**：AI 在提供代码时，必须输出完整文件内容，严禁使用 `// ...省略...`、`// 其余不变` 等占位符，除非用户明确说"只给我改动部分"。

### 1.7 Git 管理：小步快跑，一功能一 Commit
* **原则**：利用 Git 进行精细化版本控制，方便随时无损回滚。
* **AI 行为规范**：
  * 每当在 Unity 中实现并验证完一个独立子功能（例如：完成了 `MapDataStore.cs` 基础定义、完成了 `TerrainLayerGen.cs` 核心生成等），立即执行一次 Git 提交。
  * Commit 提交信息需简洁明了，采用规范的 `feat: ...` 或 `fix: ...` 格式（例如：`feat: create MapDataStore singleton and core structs`）。

### 1.8 代码自审与 Review
* **原则**：写完一段代码后，AI 必须立即进行自我 Review，排查隐患。
* **AI 自审检查问题**：
  > **"这段代码有没有潜在的 bug 或性能问题？"**
* **Review 重点**：
  * **空指针异常 (NullReferenceException)**：引用类型、Unity 组件、未初始化的数组是否做了空值校验或安全兜底？
  * **性能瓶颈**：Update 中是否有高频的 `GetComponent`、`Find`、或者大数组的频繁 GC 内存分配？
  * **逻辑边界**：数组边界是否会越界？除法中除数是否可能为 0？
  * **说明书对齐**：实现的枚举值、常量数值、结构体字段、阈值分段是否与设计说明书逐项核对？任何与说明书不一致的设计改动，须向用户说明原因并获得确认，不得擅自替换或自创。

### 1.9 变量生命周期同步管理规则（增删模块联动）
* **新建/引入模块时**：
  * 只要新建了代码模块，或者使用了新的核心变量/属性/常量，在**代码编写完成后**，必须立即将这些新变量的信息同步写入 `变量.md` 文件中。
  * 登记时，**必须确保大小写与 C# 源码中完全一致**，并详细编写好每个变量**在系统中的实际作用与影响**。
* **删除/废弃模块时（注意先后顺序与前置审批）**：
  * **跨模块删除前置审批**：如果因为功能调整或重构，需要删除**其他文件、其他代码模块或外部逻辑**（即“正在主力编写的文件 A 却去删文件 B 的内容/逻辑”此类操作），**必须在动手前，将要删除的模块、代码和原因简要向用户做介绍**。在**得到用户明确许可（发令）后**，才能进行删除操作。
  * *例外情况*：如果是针对当前主力编写的同一个文件，在开发迭代过程中正常的、多次迭代的局部代码删减，则不需要每次向用户申请审批。
  * **变量同步清理**：在确认能够删除并准备实际动手前，必须先在 `变量.md` 中核查该模块所用到的登记变量，**在 `变量.md` 中删干净这些记录后，才可以物理执行代码层面的跨模块删除**。

### 1.10 已知陷阱（必须规避）
* **严禁调用 `InitArrays()` 做兜底初始化**：该方法会清空全部五个数组，每层只能单独初始化自己的层，例如 `store.ResourceLayer = new ResourceData[MapDataStore.MAP_SIZE, MapDataStore.MAP_SIZE];`。
* **长整型取模防溢出**：对 `long` 型哈希值取模必须用 `((val % N) + N) % N` 形式，严禁直接 `% N`（负数结果）或对 `long.MinValue` 取绝对值（溢出）。
* **long 转 int 作随机种子**：使用 `(int)(seed ^ (seed >> 32))` 而非强转或截断。
* **ID 数组长度必须 >= 对应 MAX 常量**：若定义了 `WONDERS_MAX = 4`，则 `WONDER_IDS` 数组长度必须 >= 4，严禁出现数组长度小于最大目标数量，否则导致隐性重复抽取或越界。
* **外圈地形候选门槛不得过严**：在 `ringDistance > 50` 的极危险外圈放置世界建筑/奇观时，严禁将候选格限定为 `PLAINS`，应使用"非 WATER"作为最低门槛，否则外圈几乎无法找到足够候选格。

## 2. 代码命名规范（C# / Unity）

为了保持代码的统一性，所有 C# 代码均采用业界标准的 Unity 命名风格：

| 元素类型 | 命名规则 | 示例 | 备注 |
| :--- | :--- | :--- | :--- |
| **类 (Class) / 接口 (Interface)** | PascalCase | `MapDataStore`, `IClimateController` | 接口以大写 `I` 开头 |
| **结构体 (Struct) / 枚举 (Enum)** | PascalCase | `ResourceData`, `TerrainType` | |
| **公共方法 (Public Method)** | PascalCase | `InitArrays()`, `GetClimateData()` | 动词开头，清晰表达意图 |
| **私有方法 (Private Method)** | PascalCase | `CalculateDangerBias()`, `ApplyFog()` | |
| **公共变量/属性 (Public Variable/Property)** | PascalCase | `CurrentSeed`, `TerrainLayer` | 属性可配合 `{ get; private set; }` |
| **私有/保护字段 (Private/Protected Field)** | camelCase (带下划线) | `_mapSize`, `_staticClimate` | 统一以 `_` 前缀开头，便于区分局部变量 |
| **局部变量 (Local Variable)** | camelCase | `ringDistance`, `noiseValue` | |
| **常量 (Constant)** | ALL_CAPS | `MAP_SIZE`, `CENTER` | 下划线分割单词 |
| **枚举值 (Enum Members)** | ALL_CAPS | `PLAINS`, `MOUNTAIN`, `WATER` | |

字段命名一致性补充：MapDataStore 中所有公共数组字段统一使用 PascalCase（如 TerrainLayer、BuildingLayer）。AI 在任何文件中引用这些字段时，必须与 MapDataStore.cs 源码中的实际命名完全一致，不得凭记忆书写 camelCase 形式（如 terrainLayer、monsterFogLayer）。
